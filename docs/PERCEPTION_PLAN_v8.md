## 〇、v7 缺点审查（诚实版）

| v7 缺点 | 后果 | v8 修正 |
|---|---|---|
| 依赖 Python（trimesh/PaddleOCR/NIMA）| 每加一个 Python 库 = 新环境/新步骤 | **Rust 原生感知核（percept-core 二进制）** |
| 图像处理过度设计 | 截图每次都上模型，浪费 | **图像 = 嵌入检索直配（直找）** |
| 模型完整性无边界 | 一直堆维度 | **"看得懂就行"——有界完整性** |
| 视觉理解依赖大模型 | 显存/延迟高 | 小模型 ONNX + Rust 推理（ort） |

## 一、Rust 替代 Python（语言栈统一）

### 核心决策：复用 unified-rx 已有的 rx-core 模式

```
已有：rx-core（Rust 纯函数内核）+ server.py 子进程接线（R1 已验证，34ms/千次）
新增：percept-core（Rust 感知核）——同一模式，零新架构
```

| 感知功能 | Python 版（v7） | **Rust 版（v8）** | 省掉的步骤 |
|---|---|---|---|
| GLB 解析 | trimesh（Python） | **cgltf/gltf-rs（Rust）** | 装 trimesh、进程转换 |
| 网格质量 | trimesh 分析 | **Rust 手写几何算法**（退化三角/非流形/面积/体积） | Python 环境 |
| 图像嵌入检索 | CLIP（Python+torch） | **candle/ort 跑 ONNX 嵌入（Rust）** | torch 2GB 依赖 |
| 模型推理 | transformers（Python） | **ort（Rust onnxruntime 绑定）** | Python 运行时 |
| 图片解码 | PIL（Python） | **image crate（Rust）** | PIL |
| OCR（若需要） | PaddleOCR（Python） | **tesseract Rust 绑定 / 嵌入检索替代** | paddle 依赖 |

**"用 Rust 替代那些模型会怎么样？" → 答案：**
- 模型本身不换（还是 ONNX/GGUF），换的是**跑模型的引擎**（Python→Rust ort/candle）
- 省掉：Python 环境安装、进程启动、数据序列化往返、版本冲突
- 结果：**工具链 = server.py + 多个 Rust 二进制（rx-core/percept-core/…）**，单语言部署

## 二、穿透引擎插件（核心——"在引擎里面找"）

### 形态：Bevy 插件（game 侧） + MCP 工具（工具箱侧）

```
VoxelForge 游戏侧（Rust）：
  └─ unified_rx_percept 插件（编译进游戏）
       ├─ 场景导出：ECS 实体/组件/父子/变换 → 本地共享文件或管道
       ├─ 几何导出：网格顶点/索引/法线/包围盒 → 二进制快照
       ├─ 属性导出：组件属性表（Collider/Transform/Material/自定义 def）
       └─ 快照更新：差分（只推变更）——v5 的差分思想落进插件

工具箱侧（unified-rx）：
  ├─ engine_query 工具 → 读插件快照（不是猜，是真相）
  ├─ scene_export 工具 → 场景图（实体+属性）
  └─ mesh_scan 工具 → 几何快照扫描（本地）
```

### 感知 = 扫几何 + 往上进展 + 扫属性（你的原话落地）

```
一扫：扫整个多边形（网格几何）
  mesh_scan → 顶点数/面数/包围盒/三角质量（本地 Rust，0 显存）

二进展：往上进展（层级/依赖）
  scene_export → 实体树/父子/装配关系/依赖链
  （"这个模块挂在哪、依赖谁、谁依赖它"——repo_graph 的 3D 版）

三扫属性：知道属性是什么、怎么改
  attribute_scan → 组件属性表（Collider 尺寸/Transform/材质/def 字段）
  → 输出："Collider 比网格大 20%（x 轴）→ 改 collider.x = 0.8"
  （属性+改法建议 = 可行动感知，不是只报现象）
```

**完整性边界：看得懂就行**
- 扫到什么程度停？→ 智能体/人能理解场景的程度（结构+关键属性+异常）
- 不追求全维度数字孪生——**有界完整性**（够用即停）

## 三、图像 = 直接找（检索直配，不上大模型）

### 原则：图像只做"找"，不做"分析"

```
❌ 过度设计：截图 → 视觉大模型 → 描述 → 判断（慢、贵、显存）
✅ 直找：图像 → 嵌入向量 → 与目标库/历史图余弦匹配 → 直接命中

场景：
  截图找相似资产："这个截图像哪个 GLB 渲染？" → 嵌入直配
  找重复 UI："这个按钮样式之前出现过吗？" → 嵌入直配
  异常对照："当前画面 vs 正常帧" → 向量距离 > 阈值 → 异常
```

### 技术（Rust 原生）

| 用途 | 实现 | 显存 |
|---|---|---|
| 图像嵌入（找相似） | **candle 跑 CLIP/BGE ONNX**（Rust） | ~0.5G 按需 |
| 图像检索索引 | **已有 kb_query（search_index）** + 嵌入向量列 | 0 |
| 图像质量（可选） | BRISQUE（Rust 重实现，纯 CPU） | 0 |

**图像不解释、不描述、不问答——只找。** 需要理解时（深层）是另一个步骤（大模型 API 按需）。

## 四、分层职责（最终版）

```
┌─ 感知层（Rust 原生，本地，0-0.5G）──────────────┐
│  穿透引擎插件：mesh_scan / scene_export /        │
│  attribute_scan（扫几何+进展+属性）              │
│  图像直找：embed_search（嵌入匹配）              │
├─ 理解层（按需，小模型 ONNX，~1.5G）─────────────┤
│  DeepSeek-VL 1.3B（视觉单元扫描——"哪个是哪个"）│
├─ 深层层（另一个步骤——大模型 API，0 显存）───────┤
│  "看得懂之后要怎么办"→ DeepSeek 综合/建议        │
└─ 语言栈：全 Rust（percept-core 二进制）+ Python 仅剩 server.py 壳
```

**"最深层是另一个步骤"** → 感知（本地扫）≠ 理解（小模型）≠ 深层决策（API）——三层分开，按需启动。

## 五、技术选型（Rust 栈实测）

| 用途 | Rust 库/方案 | 说明 |

| 图像直找 | 嵌入 + kb_query（已有） | 复用 |
| 数据交换 | JSONL/二进制快照（已有模式） | 复用 |
