## 〇、三层架构（最终定稿）

```
┌─ 宏观层（统筹/生成）──────────────────────────────────┐
│  目标：生成项目的"整体感知模型"（细致、可查询）        │
│  调度：按场景/功能编排单元（依赖序、并行度）            │
│  总性能：显存预算（≤2G）+ 时间预算 + 优先级             │
│  聚合：各单元结果 → 融合成整体模型（JSON/图谱/索引）    │
├─ 中观层（任务单元，自治黑盒）─────────────────────────┤
│  每个功能一个单元：自己调自己、按需加载、用完释放       │
│  输出规范：检查类 → JSON；理解类 → 文字；生成类 → 资产  │
├─ 微观层（单元内部步骤）───────────────────────────────┤
│  步骤顺序/性能优化/失败降级——全是单元自己的事          │
└──────────────────────────────────────────────────────┘
```

## 一、宏观层：整体模型生成器（Model Builder）

### 目标

用户说"生成很好很细致的模型"——宏观层的产物是一个**整体的项目感知模型**：

```
VoxelForge-Nexus 整体感知模型（.unified-rx-index/percept-model.json）
├─ 结构维度：代码图（755 符号/2358 边/36 模块/hubs）        ← 单元：explore_code
├─ 资产维度：GLB 清单 + 网格质量 + 规范符合度               ← 单元：check_mesh_quality ×N
├─ UI 维度：UI 树快照 + 布局断言（运行时）                  ← 单元：detect_ui_issue
├─ 物理维度：碰撞体一致性 + 刚体引用有效性                  ← 单元：check_collider
├─ 场景维度：场景图结构 + 实体统计                          ← 单元：scene_export
├─ 质量维度：lint/漏洞/风险汇总                             ← 单元：detect_code_issue
└─ 记忆维度：相关教训召回（LSE）                            ← 单元：recall_lesson
```

**整体模型 = 各单元结果的聚合体**——按需逐个单元跑（省显存），宏观层融合（出整体）。

### 生成流程（宏观调度）

```
generate_percept_model(root):
  1. 预算规划：总显存 ≤2G / 总时间 ≤N 秒 / 优先级排序
  2. 单元编排：按依赖序调度（结构→资产→UI→物理→场景→质量→记忆）
     - 并行度 = 显存预算 / 单元峰值（宏观层算，不是单元算）
     - 单元之间可配合：check_mesh_quality 发现破面 → 自动触发 check_glb_spec
  3. 逐个执行：每个单元按需加载自己模型 → 跑 → 释放（显存峰值可控）
  4. 聚合融合：各单元 JSON → 统一 schema → 整体模型
  5. 产出：percept-model.json + 人类可读摘要（文字）
```

### 检查类输出 = JSON（你定的格式）

```json
{
  "task": "check_mesh_quality",
  "target": "assets/models/Door.glb",
  "ok": false,
  "findings": [
    {"severity": "high", "type": "degenerate_triangle", "count": 3, "indices": [12, 45, 78]},
    {"severity": "high", "type": "non_manifold_edge", "count": 1, "edges": [[5, 6]]},
    {"severity": "medium", "type": "unit_mismatch", "detail": "疑似厘米（应为米）"}
  ],
  "advice": "建议修复退化三角后重新导出（见 MODELING_EXPORT_GUIDE.md 第 3 节）"
}
```

**JSON 给程序/宏观层消费，文字给智能体/人消费——检查类两者都出。**

## 二、中观层：任务单元规范（v6 确认 + 补完）

### 单元输出三类格式（新规范）

| 单元类型 | 输出格式 | 消费者 |
|---|---|---|
| **检查类**（mesh/UI/code/collider） | **JSON**（结构化 findings + advice） | 宏观层聚合、智能体 |
| **理解类**（scene_qa/describe） | 文字（精炼 + 依据） | 智能体 |
| **生成类**（蒸馏/训练/导出） | 资产（模型文件/索引） | 系统 |

### 单元之间的"配合"（你说的"还要再配合"）

```
配合规则（宏观层定义依赖边，单元自己不管）：
  check_mesh_quality 发现 non_manifold  → 触发 check_glb_spec（规范复核）
  detect_ui_issue 发现重叠              → 触发 engine_query（拿精确坐标）
  check_collider 发现尺寸不匹配          → 触发 explain_symbol（查 def 定义）
  scene_export 发现异常实体              → 触发 scene_qa（视觉确认）

每个单元仍是自治黑盒——配合是宏观层把 A 的输出喂给 B，不是 A 知道 B。
```

## 三、总性能适配（宏观层管，单元不操心）

| 预算项 | 宏观层职责 | 单元职责 |
|---|---|---|
| 显存 | 规划并行度（≤2G 峰值）| 自己按需加载/释放 |
| 时间 | 总预算、超时熔断 | 自己内部优化（缓存/并行） |
| 优先级 | 排序（先结构后视觉）| 不关心 |
| 失败 | 降级链（单元A失败→B兜底）| 自己报错即可 |

**"最终好像还是要适配总性能" → 宏观层有全局视角：知道哪个单元重、哪个轻，
安排并发/串行；单元只有局部视角（自己那点事）。**

## 四、整体模型能干什么（演示效果——你要的"很细致"）

```
演示 1：宏观生成

演示 4：单元配合
  调用：check_mesh_quality(Door.glb) 
  输出：JSON + 自动触发 check_glb_spec 的复核结果（宏观层串起来的）
```

## 五、落地顺序

| 优先级 | 做什么 | 说明 |
|---|---|---|
| P0 | **单元壳规范**（TaskUnit 基类：输入→输出，检查类 JSON） | 纯代码，无模型 |
| P0 | **三个纯函数单元**：explore_code / check_mesh_quality / check_collider | 0 显存 |
| P1 | **宏观层 generate_percept_model**（编排+聚合+预算） | 先聚合纯函数单元 |
| P1 | **detect_ui_issue**（DeepSeek-VL 按需） | 视觉单元进宏观 |
| P2 | scene_qa / segment_objects / 蒸馏自训 | 模型单元+训练 |

## 一句话

> **最终架构：微观单元自治（自己调自己、按需加载、检查出 JSON）、
> 中观配合（宏观层串依赖边，A 输出喂 B）、宏观统筹（整体模型生成器——
> 预算规划 + 编排 + 聚合，产出项目"数字孪生"整体感知模型）。
> 显存靠单元按需省，细致靠宏观聚合，性能靠宏观适配——三件事各归其位。**
