# PR 纪律（对所有本人贡献的仓库一体适用）

一个 PR 只承载一个功能。这不是形式洁癖：review 面小、单测归位、出问题可单独回滚、
维护者能按价值逐个收——捆包 PR 只要一环卡住，整包都合不了。

## 四条硬规则

1. **一个 PR 一个功能。** 主题一句话说得清；diff 里只出现为这个功能服务的改动。
2. **过程里发现的问题，不许搭车修。** 另开 PR / issue 修，正文必须引用它出自哪个
   PR / issue 的哪一步（"做 X 时发现 Y"），让因果链可追。
3. **依赖变更自成 PR。** 加 / 升 / 删依赖一律单独一个 PR，正文引用需要它的那个
   PR / issue（"为 #N 引入 X"）——依赖有独立的回滚与审计面，混进功能 PR 会放大
   爆炸半径（Dependabot 的每次升级天然就是这种 PR，照收即可）。
4. **捆绑的历史 PR 要拆。** 已 push 未 review 的多功能 PR，按功能拆成独立 PR
   （各自从主干切分支），原 PR 关闭并留评论指向拆分结果；已合并的不重写历史。

## 边界判定

- **CI 接线**：为一个功能服务的 workflow 接线算该功能的一部分；独立成门（如依赖
  审计、词汇扫描）就算独立功能，另开 PR。
- **文档同步**：与功能同一提交（目标仓库的 contributing 约定优先于本文件）。
- **连续依赖的功能**：按依赖顺序排队，每个 PR 正文写明"依赖 #N 先合"；不把多个
  功能塞进同一个 PR 换取免排队。

## 出处（本文件的由来）

- qingjian PR #234（iOS + Android + OHOS 三个目标捆一个 PR）→ 拆成三个；
- RUST-WL PR #5（棘轮门禁层 + cargo-deny 依赖审计捆一个 PR）→ 拆成两个；
- 依赖更新 CI 覆盖本人全部活跃仓库，依赖升级一律走 Dependabot / 独立 PR。
