# 扫描标准（SCAN-POLICY）

> 定稿：2026-09-04，项目所有者要求。起因：第一次全仓"深度"扫描只做了静态分析，
> 58 条报警经逐条核实仅 3 条为真，误报率 95%；且那次扫描由主控会话亲自执行——
> 扫描器跑在被扫项目所在的环境里，自己扫自己。这两件事都不标准，自此作废。

## 一、四条铁律

### 铁律 1：禁止自扫自

扫描器**不得**扫描它自身运行所依赖的项目或宿主。自己扫自己 = 既当运动员又当裁判：
扫描器自身有什么缺陷（解析不了某语法、识别不了某入口、调用图建不起来），就会直接
变成误判或漏判，而且没人能发现——裁判的错只有更高的裁判才能纠。

- 执行扫描的必须是**独立的一方**（独立智能体 / 独立环境 / 其他引擎）。
- 主控会话（日常干活的这个 AI）只负责三件事：派发扫描任务、逐条复核证据、修真问题。
  **不亲自跑扫描器。**
- 扫描工具本身如果要更新/升级，同样由独立方验证，不由它自己验证自己。

### 铁律 2：副本隔离

扫描对象永远是**复制品**，不是原件。

- 先克隆：`git clone` 出扫描专用副本（应用类用本仓 `app_clone`，落点固定、带指纹清单）。
- 副本放进沙箱：`UNIFIED_RX_SANDBOX` 等环境变量只指向副本目录。
- 原件在扫描全程只读不动；扫描中产生的一切写操作（探针脚本、fuzz 载荷、临时输出）
  只落在副本和专用临时目录里。
- 扫完的副本用完即清（`app_clean` 同款纪律：严格限沙箱内，越界一律拒绝）。

### 铁律 3：静态只是初筛，不是结论

静态扫描（模式匹配、AST 规则）给出的每一条都是**假设**，不是**发现**，更不是**结论**。
证据：2026-09-04 那次扫描，`fs.py/ide_edit.py/lsp.py/game.py/meta.py` 的全部指控都是
误报——入口明明有 `_fs_resolve` 沙盒校验，扫描器跟不过那一跳。没有第二层验证，
静态结果只能当线索清单用。

### 铁律 4：结论纪律

- 扫描器状态为 `incomplete / inconclusive / partial` 时，结果只能作线索，**不得当"通过"**。
- 报告必须带：扫描 ID、封印标识（seal）、覆盖状态（哪些阶段没跑完）、已验证清单、
  未验证清单。
- **永远不允许宣称"项目安全"**，只允许陈述事实："查了什么、怎么验的、验出什么、
  剩下什么没验"。（本条与 git 提交钩子的既有提醒一致。）

## 二、标准扫描流程（五步）

| 步骤 | 动作 | 执行者 | 产物 |
|---|---|---|---|
| 1 静态初筛 | 模式匹配级全仓扫描 | 独立扫描智能体 | 假设清单（不是发现） |
| 2 复制隔离 | clone 副本 + 沙箱指向副本 | 独立扫描智能体 | 隔离的扫描环境 |
| 3 动态验证 | 真实运行（见下节） | 独立扫描智能体 | 逐条真/伪证据 |
| 4 主控复核 | 对照源码逐条判真伪、定级 | 主控会话 | 复核记录（真问题/误报） |
| 5 出结论 | 修复真问题 + 存档封印报告 | 主控会话 + 所有者 | seal 报告 + 修复 PR |

## 三、动态验证对本项目意味着什么

"动态"不是抽象概念，落到 unified-rx-mcp 就是四类真实运行用例（全部在副本沙箱里跑）：

1. **MCP 协议层**：向 `server.py` 的 stdio 打畸形 JSON-RPC、超长行、非 UTF-8 字节、
   交叉并发请求——协议解析不许崩、不许吞（现成基线：`tests/test_security_fuzz.py`、
   `tests/test_s29_fuzz.py`，扫描时提升为必跑步骤）。
2. **工具层**：带 `__authorized: true` 真调写/执行类工具，验证授权门**真的挡得住**
   不带授权的调用（基线：`tests/test_s73_scan_findings.py`、`test_s61_hardening.py`）。
3. **路径层**：沙盒逃逸用例——`../`、symlink/junction 指沙盒外、盘符大小写、
   realpath 绕过（基线：`test_attack.py`、`test_s42_guards.py`）。
4. **环境层**：`UNIFIED_RX_SANDBOX` 未设置 / 空 / 垃圾值 / `*` 四态下 fail-closed
   语义必须成立（基线：`test_s62_caps.py`）。

每类用例的通过标准：预期拒绝的全部拒绝、预期放行的全部放行、失败必须带
`error_detail`（S72 契约）可定位——不允许静默降级。

## 四、案例存档（本标准的直接动因）

- **扫描**：`scan-2026-09-04T15-42-49.068Z-9a7abe77e6a1`，seal `sha256:32bfc234…f3189`，
  depth=deep，136 文件全解析，状态 **inconclusive（partial）**：威胁模型阶段识别出
  0 个入口点、58 条发现 0 条做过二次验证、调用图未建立。
- **结果**：58 条 → 真问题 3（`code_coverage` 无授权门+路径不过沙盒；`lesson` 显式
  `lessons_dir` 任意写；`app_clone` 整目录读取无授权）→ S73 全修，12 条回归测试钉死。
- **误报 55 条**：约 40 条在 `bench/`（本地实验脚本，不暴露给 AI，无攻击面）；其余
  `fs/ide_edit/lsp/game/meta` 各条均核实入口已有沙盒校验或硬编码 127.0.0.1。
- **自省**：该次扫描由主控直接执行、且只有静态一层——正是本标准禁止的两个动作。

## 五、未来升级方向（如实定界：未做，仅规划）

- 调用图 / 污点分析：当前扫描引擎 pathAnalysis 阶段空转（0 函数 0 边），换能建图
  的引擎后，"扫描器跟不过 _fs_resolve 那一跳"这类误报可望自动消除。
- 双引擎交叉验证：两个独立扫描器互查，两边都报的优先复核。
- 协议模糊测试常态化：从 pytest 用例提升为每次合入 main 前的固定门禁。
- 以上任何一项落地时，执行者仍须遵守铁律 1/2：独立方、副本、沙箱。
