# LIBRARY-POLICY.md —— 库选型理念（S135 立文；用户指令，**跨项目适用**）

> 用户原话（2026-09-14）：「有好多库你都是可以看看的，但是我希望你在这些库的
> 情况下还能优化、省 token——最好是可以用到库；但用还是看这个库的**理念和整个
> 设计**符不符合。不仅仅是我开发你、你协助我开发其他的东西，都是要这个的。
> 把上面记在文档和理念之一。然后就继续做 Rust 吧，大胆的用最新技术——有些库
> 可能因为版本不好所以导致某些设计不行，搞库最好都是搞前沿的，反正大部分的东西
> 最好都是搞前沿的东西。」

## 一、三问（用库还是自研，按此顺序过）

1. **理念与设计契合度 > 名气**——先读这个库"想成为什么"（API 形状、扩展点、
   依赖姿态、失败语义），再问"跟我们要做的事是不是同一种做法"。设计不合，
   名气再大也不用（"用还是看这个库的理念和整个设计符不符合"）。
2. **版本前沿性**——"这个库不行"经常是**旧版本不行**：候选必须看当前版本
   （活跃维护/近期 major 的设计改进）；老 API 当基线做的判断要重估。
   前沿优先（"搞库最好都是搞前沿的"），但前沿不等于 beta——是**当前最新稳定线**。
3. **Token 账**——是省 token 的硬约束：自研一个中核 = agent 要读、写、测、
   维护四份 token；库 = 探测 + 接口调用 + 解析三件套（本仓已有成熟薄壳模式）。
   **能用成熟库的地方优先用库**；只有"理念不合/红线不允许/库本身是坑"才自研。

三问冲突时的优先级：**红线（安全/审计面）> 理念契合 > 前沿性 > 省 token**。

## 二、本仓（unified-rx-mcp）红线下的合法形态

本仓 red line：Python 纯 stdlib、Rust `[dependencies]` 恒空（审计面/供应链，
见 HARDENING §一/VULN-HUNTING §五）。因此"用库"在**本仓**的合法形态 =
**外部工具经能力探测薄壳接入**（既有成熟模式：LSP 接 rust-analyzer/pylsp、
ast-grep、OpenCL 运行时、codegraph、ruff/mypy/pyflakes、cargo/go/javac/gcc）：
装了就用、没装**如实报**（skipped/清晰错误），零 pip/crate 依赖不变。
== 本仓要新引入第三方 crate 时，走既有程序：先改红线文档（VULN-HUNTING §五）
并说明理由——那正是"理念契合度"审查的实例 ==。

## 三、其他项目（如 VoxelForge 等）可直接用库，但同过三问

- 给用户的其他项目做技术选型：按 §一 三问；"最新技术"包括**语言特性**
  （新版本语义/新标准库能力）**优先于**第三方库——语言自带的新能力零依赖、
  零供应链面，是"前沿 + 省 token"双优解；
- 库里挑"设计对路"的那一个：同类库先比**设计哲学**（例：数据并行优先
  进程内零拷贝而非分布式协议；CLI 解析优先声明式 schema 而非手撸 argv）。

## 四、操作化（每次设计新能力时的动作）

1. 列 2–3 个候选（含**当前版本**的前沿方案），各写一行"理念一句话"；
2. 过三问 + 红线优先序，**写下选择与理由**（入了本次改动说明/ROUNDLOG）；
3. 接入形态默认**薄壳**（探测→调用→解析→如实降级），不把库焊进核心；
4. 用了库就**别重复造**——同一能力禁止两套实现（本仓 S125 教训延伸）。

## 五、反面清单（踩过的坑，持续追加）

- "能跑的组合就收工"——同一能力两套实现（S124 cargo 误诊教训的同族）；
- 旧版本设计缺陷当"库不行"结论（先看最新版本再下结论）；
- 为省 token 而自研（省了读库的 token，赔上写+测+维护三倍）；
- 为用库而用库（理念不合硬接 = 长期 token 黑洞）。
